# Как запустить и проверить

**Дата:** 1 октября 2026
**Контракт:** 1.0.0 — тот, который backend реализует

У системы два рабочих режима, и различает их источник кадров у агента:

- **демо-режим** — `camera.source = "virtual"`, агент отдаёт серверу готовый
  видеофайл как поток. Всё остальное настоящее: сервер, распознавание, события,
  записи, приложение. Это основной способ показать систему и проверить её
  целиком, не падая перед камерой;
- **прод-режим** — `camera.source = "rtsp"`, агент берёт кадры с настоящей
  IP-камеры. От демо отличается только этими двумя строками в конфигурации
  агента; сервер и приложение разницы не видят.

Способы 1 и 2 ниже — не режимы, а приёмы диагностики: они отделяют «приложение
не работает» от «сервер не отдал» и проходятся за минуту каждый.

| Способ | Что проверяет | Что нужно |
|---|---|---|
| 1. Приложение одно, без сервера | Все шесть экранов, матрицу состояний, тревогу, историю, кадр | Только эмулятор |
| 2. Сервер без агента | Настоящую активацию, вход, токен, `/agents`, пустую историю | Docker |
| 3. **Демо-режим** | **Полный путь: падение → событие → кадр → видео** | Docker, Python 3.13, видеофайл |
| 4. Прод-режим | То же, но от настоящей камеры | Docker, Python 3.13, IP-камера |

## Способ 1. Приложение одно, без сервера

```bash
cd ~/AndroidStudioProjects/terentiy_mobile
./gradlew :app:testDebugUnitTest :app:assembleDebug :app:lintDebug   # проверка
adb uninstall ru.terentiy.mobile                                     # если стояла прошлая версия
./gradlew :app:installDebug
```

Удаление обязательно при смене версии: прежняя сборка оставляет в защищённом
хранилище сессию другого формата.

Открыть «Терентий» в эмуляторе. На экране подключения внизу — переключатель
**«Показ без сервера»**; по умолчанию он выключен, для этого способа его надо
включить. Переключатель есть и в Профиле, но до активации Профиля не существует,
поэтому выбор делается здесь.

**Сценарий:**

1. **Подключение.** Адрес — любой корректный (`http://10.0.2.2:8080`), код
   установки — от 4 символов, имя, PIN из шести цифр и повтор. Кнопка
   «Подключиться» неактивна, пока форма неполная.
2. **Первые три секунды** на главной — «Состояние неизвестно»: агент ещё не
   отчитался. Это отдельное состояние, не поломка.
3. **Дальше** — «Наблюдение работает», пульсирующие кольца, строки камеры, связи
   и потока кадров, время последнего кадра.
4. **На 23-й секунде** — коралловый баннер «Падение» с основанием «Определено по
   позе человека». «Открыть событие» → карточка с настоящим кадром с камеры
   установки, блок «Подробности» разворачивается в голосование правил.
5. **«Смотреть видео»** — загрузка с прогрессом, затем проигрывание. В демо это
   тот же кадр, превращённый в шестисекундное видео с медленным наездом: настоящей
   записи падения пока нет ни у демо, ни у сервера, но проигрыватель проверяется
   целиком, включая кнопку «Открыть во внешнем плеере».
6. **Через минуту** сценарий проходит остальные состояния: кадры отстают
   (очередь 24) → камера недоступна → агент не отвечает → снова норма.
7. **История** — три события, у непросмотренных красная точка, она гаснет после
   открытия.
8. **Профиль** — имя, дом, адрес, тот же переключатель, размер кеша видео,
   прямая строка про отсутствие уведомлений, выход с подтверждением.
9. **Повторный вход** — тем же PIN. Неверный PIN демо отвергает, после трёх
   неудач вход блокируется на 15 секунд.
10. **Тёмная тема** — переключить системную настройку эмулятора.

## Способ 2. Сервер в Docker, без агента

Нужен Docker Desktop. Всё выполняется в `terentiy_ai/server`.

```bash
cd ~/PycharmProjects/terentiy_ai/server

cp .env.example .env
cp config/server.example.toml config/server.toml
cp config/installation-codes.example.toml config/installation-codes.toml
```

**Правки в трёх файлах:**

- `.env` — задать `POSTGRES_PASSWORD` (тот же пароль подставить в
  `TERENTIY_DATABASE_URL`) и `TERENTIY_TOKEN_PEPPER` (длинная случайная строка;
  её смена обнуляет все выданные токены).
- `config/installation-codes.toml` — заменить placeholder на свой код, например
  `HOME-SETUP-CODE`. Это и есть код установки, который вводится в приложении.
- `config/server.toml` — править не обязательно: пути к весам моделей там уже
  указаны как `/models/...`, то есть под Docker.

**Веса моделей** лежат в корне репозитория и монтируются в worker:

```bash
mkdir -p models
cp ../yolo26m.pt ../yolo26n-pose.pt models/
```

Без них worker не поднимется, а значит события не появятся никогда.

**Запуск:**

```bash
docker compose up --build
```

Поднимутся четыре контейнера: PostgreSQL, миграции (отработают и выйдут), API и
ML-worker. Проверка:

```bash
curl http://127.0.0.1:8080/health
# {"status":"ok","database":"ok"}
```

**В приложении:** на экране подключения переключатель «Показ без сервера»
оставить **выключенным** (это значение по умолчанию), адрес
`http://10.0.2.2:8080` — это хост-машина с точки зрения эмулятора, код установки
— свой из `installation-codes.toml`. Если приложение уже активировано в демо,
нужно выйти из аккаунта в Профиле и на экране входа нажать «Забыли PIN?».

**Что должно получиться:** активация проходит, главная показывает «Устройство
наблюдения не подключено» — агентов в базе ещё нет. История пуста. Это
правильный результат: приложение и сервер договорились.

Кнопка «Проверить адрес» на экране подключения обращается к `/health` и отличает
«сервер не отвечает» от «код установки не подошёл».

## Способ 3. Демо-режим: сервер, агент и видеофайл

Сервер из способа 2 должен работать. Агент запускается нативно, не в Docker.

```bash
cd ~/PycharmProjects/terentiy_ai/agent
python3.13 -m venv .venv
source .venv/bin/activate
python -m pip install -e ".[dev]"
cp config/agent.example.toml config/agent.toml
cp .env.example .env.local
```

В `.env.local` — только код установки; строка RTSP в демо-режиме не нужна и
может остаться закомментированной:

```dotenv
TERENTIY_INSTALLATION_CODE=HOME-SETUP-CODE
```

```bash
terentiy-agent --config config/agent.toml
```

Агент сначала активируется на сервере и сохраняет `agent_id` в
`var/state/identity.json`; при следующем запуске активация не повторяется.
Heartbeat идёт каждые 10 секунд.

**Порядок запуска важен: видео кладём в инбокс до старта агента.** Работающий
агент, постоявший с пустой очередью, новый файл уже не прочитает — он
переоткрывает его каждые 5 секунд и отпускает, не прочитав ни кадра
(бэклог §22). Правильная последовательность для повторного прогона:

```bash
# Ctrl+C в окне агента
cp var/video-archive/fall-02.mp4 var/video-fragments/run2.tmp
mv var/video-fragments/run2.tmp var/video-fragments/run2.mp4
terentiy-agent --config config/agent.toml
```

**Перед повторным прогоном того же файла перезапустите worker:**

```bash
cd ~/PycharmProjects/terentiy_ai/server && docker compose restart worker
```

Иначе подтверждённое падение получит вердикт `COOLDOWN` и события не будет:
отметка предыдущего падения живёт в памяти worker-а в шкале времени видео, а
перезапуск агента эту шкалу обнуляет (бэклог §21). Симптом ровно такой же, как
у нераспознанного падения, и виден только в диагностическом отчёте.

**Что смотреть в приложении:**

| Действие | Ожидаемо на главной |
|---|---|
| Видео проигрывается | «Наблюдение работает», камера подключена, время последнего кадра обновляется |
| Видео закончилось, инбокс пуст | «Поток с камеры прервался» — агент жив, кадров нет. Это правильный ответ, а не поломка |
| Остановить агента (Ctrl+C) | «Устройство наблюдения не отвечает» через ~30 секунд — столько сервер ждёт heartbeat |
| Положить новый файл и запустить агента | Возврат к «Наблюдение работает» |

**Проверка падения без падения.** У агента есть режим виртуальной камеры: он
читает mp4 из каталога и отдаёт его как поток. В `config/agent.toml`:

```toml
[camera]
source = "virtual"

[virtual_camera]
directory = "../var/video-fragments"
loop = true
archive_directory = "../var/video-archive"

[frames]
upload_interval_seconds = 0.25   # было 1

[video_buffer]
codec = "avc1"            # было mp4v
retention_seconds = 900   # было 60
```

**Частота кадров важнее, чем кажется.** Правило подтверждения «скорость
опускания таза» сравнивает позу с позой примерно 0.5 секунды назад, допуск
0.35–0.65 с. При кадре раз в секунду подходящей пары не существует, и правило
честно не голосует — остаётся только угловая скорость. Падение может дойти до
стадии «кандидат» и не подтвердиться, а без подтверждения события не будет. При
0.25 нужная пара — это кадр через один, ровно 0.50 секунды назад, середина
допуска.

**Кодек записи — `avc1`, а не `mp4v`.** `mp4v` это MPEG-4 Part 2; в таком виде
клип скачивается целиком и открывается **чёрным экраном** — ни `VideoView` в
Android, ни QuickTime его обычно не декодируют, причём молча. `avc1` это H.264,
который умеют все; `libx264` уже лежит внутри сборки `opencv-python`, новых
зависимостей не нужно. Проверка — на любом свежем сегменте буфера:

```bash
ffprobe -v error -show_entries stream=codec_name -of default=nw=1 \
  var/video-buffer/$(ls -t var/video-buffer | head -1)
# codec_name=h264
```

**Хранимость буфера — 900 секунд, а не 60.** Клип собирается не из исходного
файла, а из этого кольцевого буфера. Сервер просит окно падение ±15 секунд, но
на CPU распознавание отстаёт от записи на минуты: при хранимости в минуту нужные
сегменты успевают вытесниться, и событие навсегда остаётся без записи, то есть
невидимым — `/events` не отдаёт события без клипа.

**Материал для окна записи.** Сервер просит у агента ±15 секунд вокруг момента
падения. Если ролик короче, вырезать будет нечего или почти нечего. Ролики
датасетов обычно длятся 4–7 секунд и заканчиваются сразу после падения — такой
файл стоит дополнить неподвижными краями:

```bash
ffmpeg -i fall.mp4   -vf "tpad=start_mode=clone:start_duration=6:stop_mode=clone:stop_duration=18,format=yuv420p"   -r 25 -c:v libx264 -crf 26 fall-padded.mp4
```

Замороженные края честны по смыслу: упавший человек остаётся лежать.

Файл копировать под временным расширением и переименовывать после завершения
копирования, иначе агент прочитает недописанный. Во входном каталоге держите
**один** файл за прогон: при `loop = true` агент обработает все и создаст по
событию на каждый.

**После падения:** событие появляется в приложении **через 20–40 секунд** —
сервер ждёт 15 секунд пост-ролла, затем просит агента загрузить клип, и только
после загрузки событие становится видимым. Это не задержка приложения: сервер
намеренно не отдаёт события без записи. В истории об этом есть строка.

Дальше: баннер на главной → карточка события → настоящий кадр → «Смотреть видео»
→ клип скачивается с прогрессом и проигрывается. Запасной выход — «Открыть во
внешнем плеере».

## Способ 4. Прод-режим: настоящая IP-камера

От демо-режима отличается двумя строками. В `config/agent.toml`:

```toml
[camera]
source = "rtsp"   # было virtual
```

И в `.env.local` — адрес камеры с логином и паролем:

```dotenv
TERENTIY_RTSP_URL=rtsp://admin:ПАРОЛЬ@192.168.0.105:554/stream1
```

Пароль камеры держится только здесь: файл в `.gitignore`, в репозиторий не
попадает и в переписку тоже.

Сервер, приложение и правила распознавания — те же. Инбокс видеофайлов в этом
режиме не читается, `[virtual_camera]` можно не трогать.

**Что меняется в проверке:**

| Действие | Ожидаемо на главной |
|---|---|
| Камера работает | «Наблюдение работает», время последнего кадра обновляется |
| Отключить камеру от сети | «Камера недоступна» в течение ~10 секунд |
| Камера на связи, поток не идёт | «Поток с камеры прервался» — порог `stream_stale_after_seconds = 10` |
| Остановить агента | «Устройство наблюдения не отвечает» через ~30 секунд |

Частота кадров и хранимость буфера из демо-режима остаются в силе: `0.25` и
`900` выведены из физики правил, а не из способа получения кадров.

## Если что-то не работает

Порядок сужения проблемы — от сервера к приложению:

1. **Сервер жив?** `curl http://127.0.0.1:8080/health`. Если `database:
   unavailable` — PostgreSQL не поднялся, смотреть `docker compose logs db`.
2. **Worker жив?** `docker compose logs worker`. Без него кадры принимаются, но
   события не создаются никогда, и история остаётся пустой при живом агенте.
3. **Сервер отвечает, приложение нет?** Проверить референсным клиентом — он
   разделяет «сервер не отдал» и «приложение не разобрало»:

   ```bash
   cd ~/PycharmProjects/terentiy_ai/mobile-emulator
   python3.13 -m venv .venv && source .venv/bin/activate
   python -m pip install -e ".[dev]"
   cp config/mobile.example.toml config/mobile.toml
   export TERENTIY_MOBILE_INSTALLATION_CODE=HOME-SETUP-CODE
   terentiy-mobile --config config/mobile.toml health
   terentiy-mobile --config config/mobile.toml agents
   terentiy-mobile --config config/mobile.toml events
   ```

4. **Приложение молчит?** `adb logcat | grep -i terentiy` — все технические
   подробности уходят в Timber, пользователю показываются только человеческие
   формулировки.
5. **Видео скачалось, но экран чёрный.** Клип записан кодеком, который Android
   не декодирует. Проверить `ffprobe` (см. выше): нужен `h264`. Если `mpeg4` —
   в `agent/config/agent.toml` поставить `codec = "avc1"`, перезапустить агента
   и прогнать видео заново. Уже созданные события останутся с нечитаемым
   клипом: перезаписать его сервер не просит.
6. **В эмуляторе не набирается русское имя.** Ограничение клавиатуры эмулятора,
   а не приложения — поле ничего не фильтрует. Settings → System → Languages &
   input → Virtual keyboard → Gboard → Languages → Add keyboard → Русский, и
   переключать язык глобусом на пробеле. Физическая клавиатура Mac отдаёт
   эмулятору скан-коды, поэтому русская раскладка хоста не помогает.
7. **«Это устройство уже подключено»** при активации — нормальный ответ сервера
   на повторную активацию. Вход по PIN, а если PIN забыт — «Забыли PIN?» на
   экране входа выдаст устройству новый идентификатор. Прежняя запись останется
   на сервере навсегда: маршрута удаления в контракте нет.
8. **Эмулятор не видит сервер** — адрес должен быть `http://10.0.2.2:8080`, а не
   `127.0.0.1`. Для реального телефона — LAN-адрес Mac и одна сеть.

## Автоматическая проверка

```bash
./gradlew :app:testDebugUnitTest          # логика: состояния, мапперы, ошибки, лента, контракт на MockWebServer
./gradlew :app:connectedDebugAndroidTest  # экраны, нужен запущенный эмулятор
./gradlew :app:lintDebug
```

Unit-тесты не требуют ни сервера, ни эмулятора и проходят за секунды. Именно они
поймают расхождение с контрактом, если он изменится снова.
