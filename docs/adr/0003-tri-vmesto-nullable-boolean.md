# ADR-0003. Доменная модель использует Tri вместо Boolean?

**Дата:** 13 сентября 2026
**Статус:** принято и подтверждено дважды. 29 сентября драфт 1.1.0 выразил
троичность своим перечислением, и тип `Tri` был удалён как излишний. 30 сентября
реализованный контракт 1.0.0 вернул nullable-поля (`camera_connected: boolean |
null`, где `null` означает «агент ни разу не отчитался»), и `Tri` вернулся
дословно. Довод — «неизвестно» не равно «нет» — оказался верен в обеих версиях
контракта.

## Контекст

В `AgentStatus` поля `agent_online`, `camera_connected`, `stream_active`, `ml_ready`
объявлены как `boolean | null`. `null` возвращается, когда агент ни разу не присылал
heartbeat: строки в таблице `device_status` просто нет.

`null` здесь означает «неизвестно», а не «выключено». Если в коде написать
`if (camera_connected == true)`, оба случая схлопнутся в одну ветку, и пользователь
увидит «камера недоступна» там, где правда — «мы пока ничего не знаем».

Это ровно та ошибка, от которой предостерегает SDD-000 §6 и §11 применительно
к присутствию человека: «камера не работает» нельзя путать с «человека нет».
В архивном контракте v1.0 ради этого существовал `PersonPresenceState` с тремя
значениями. Принцип переносится на технические флаги без изменений.

## Решение

Доменная модель использует собственный `enum Tri { YES, NO, UNKNOWN }`.
Маппер DTO → domain — единственное место в кодовой базе, где `null` превращается
в `UNKNOWN`. Ниже по коду `Boolean?` не существует, и написать `if (flag)` невозможно.

## Последствия

- Каждая ветка UI обязана явно обработать `UNKNOWN` — компилятор этого требует.
- Тексты интерфейса различают «Камера недоступна» и «Данные ещё не поступали».
- Когда backend начнёт отдавать присутствие человека, тот же тип применяется к нему
  без новых абстракций.
- Unit-тест проходит по всей матрице состояний, включая `UNKNOWN` в каждом поле.
