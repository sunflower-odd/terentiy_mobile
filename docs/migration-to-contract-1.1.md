# Миграция на контракт 1.1.0-draft

**Дата разбора:** 29 сентября 2026
**Источник:** `terentiy_ai`, коммит `2d5141d` от 22 сентября
**Состояние:** анализ, код не изменялся

---

## 1. Что произошло

В `terentiy_ai` пришли два коммита.

**`c65866a` (20 сентября)** — простейшая детекция падения. Правила в
`src/terentiy/fall_rules/` (угловая скорость, соотношение сторон, ориентация тела,
вертикальная скорость), трекинг в `edge/tracking.py`, переработан агент: появились
`frame_source`, `video_source` и фабрики. Результат детекции никуда не передаётся —
оседает в отчёте `src/experiment/pose_observation_report.py`.

**`2d5141d` (22 сентября)** — ТЗ на мобильное приложение
(`contracts/android-demo-mobile-tz.md`), сториборд из пяти экранов
(`contracts/android-ui-storyboard.md`, картинки в `docs/assets/`) и переписанный
контракт `mobile-server.openapi.yaml`, версия **`1.1.0-draft`**.

Назначение демо по сториборду: показать акселераторам сценарий
активация → включение наблюдения → тревога о возможном падении → доказательный
кадр и 30-секундный клип.

## 2. Ключевой факт: backend контракт не реализует

Проверено поимённо по `src/` на коммите `2d5141d`:

| Маршрут нового контракта | Упоминаний в `src/` |
|---|---|
| `POST /api/v1/auth/register` | 0 |
| `POST /api/v1/auth/login` | 0 |
| `POST /api/v1/auth/refresh` | 0 |
| `POST /api/v1/auth/logout` | 0 |
| `GET /api/v1/home` | 0 |
| `PUT /api/v1/agents/{id}/observation` | 0 |
| `GET /api/v1/events`, `/events/{id}` | 0 |
| `GET /api/v1/media/{id}` | 0 |

Сервер отдаёт те же семь маршрутов, что и в версии 1.0.0: `/health`,
`/mobile/activate`, `/mobile/login`, `/agents/activate`, `/agents`,
`/agents/{id}/status`, `/agents/{id}/latest-image`. Схема БД не менялась, таблицы
событий нет, детекция падения к backend не подключена.

**Вывод:** контракт 1.1.0 — спецификация вперёд, помеченная `draft`. Начинать
перестройку приложения означает снова работать против мок-сервера, с риском
расхождения. Отличие от августовской ситуации в том, что контракт написан
автором backend, а не мобильной стороной в одиночку — шансы на совпадение
существенно выше, но проверяется это только реализацией.

## 3. Построчное расхождение

### 3.1. Аутентификация — переделана полностью

| 1.0.0 | 1.1.0-draft |
|---|---|
| `POST /mobile/activate`: `installation_code` + `device_id` + `pin` (`^\d{6}$`) | `POST /auth/register`: `activation_code` + `device_id` + `username` (3–64, `^[A-Za-z0-9._-]+$`) + `password` (**12–128**) + необязательный `recovery_contact` (e-mail) |
| `POST /mobile/login`: `device_id` + `pin` | `POST /auth/login`: `device_id` + `username` + `password` |
| — | `POST /auth/refresh`: обязательная ротация refresh-токена; повторное предъявление использованного токена отзывает всю token family устройства |
| — | `POST /auth/logout` → `204` |
| — | `POST /auth/password-reset/request` → всегда `202`, чтобы не раскрывать существование логина |
| — | `POST /auth/password-reset/confirm` → `204`, все прежние сессии отзываются |
| `MobileToken`: `access_token`, `token_type`, `household_id`; бессрочный | `Session`: `access_token` (**15 минут**), `refresh_token`, `access_expires_at`, `refresh_expires_at`, `household_id` |

**PIN исчезает из системы полностью.**

### 3.2. Главный экран

`GET /agents` → `GET /home`, и это другая модель.

| 1.0.0 `AgentStatus` | 1.1.0 `AgentHomeStatus` |
|---|---|
| `id`, `household_id`, `name`, `camera_id`, `software_version`, `created_at` | `agent_id`, `name` |
| `online`, `agent_online` (nullable) | `agent_online` (обычный boolean) |
| `camera_connected`, `stream_active` (nullable boolean) | `camera`: enum `connected / unavailable / unknown` |
| `ml_ready`, `queue_size`, `last_frame_at`, `reported_at` | `updated_at` |
| — | `observation`: `ObservationStatus` |

Обёртка ответа тоже другая: вместо `{items: [...]}` приходит `HomeSummary` с
`agents`, `unreviewed_event_count`, `latest_unreviewed_event` и
`poll_after_seconds` (константа **5**, против наших 20).

Отдельно стоит отметить: троичное состояние камеры, ради которого в приложении
введён `Tri`, теперь закреплено в самом контракте как enum с `unknown`. Решение
из [ADR-0003](adr/0003-tri-vmesto-nullable-boolean.md) подтвердилось со стороны
backend; сам тип `Tri` после миграции станет не нужен для камеры, но останется
полезен, если появятся другие nullable-флаги.

### 3.3. Управление наблюдением — новое

`PUT /api/v1/agents/{agent_id}/observation`, тело `{ "desired_state": "enabled" | "disabled" }`,
ответ `202` + `ObservationStatus`.

Состояния: `disabled`, `starting`, `enabled`, `stopping`, `unavailable`.
Команда доставляется агенту асинхронно, промежуточные состояния держатся до
следующего heartbeat.

### 3.4. События — новое

- `GET /api/v1/events` — курсорная пагинация: `cursor`, `limit` (1–100, по умолчанию 30),
  фильтр `agent_id`. Ответ `EventPage` с `items` и `next_cursor`.
- `GET /api/v1/events/{event_id}` → `FallEvent`.

`EventPreview`: `id`, `agent_id`, `event_type` (константа `possible_fall`),
`occurred_at`, `severity` (константа `urgent`), `reviewed`.

`FallEvent` добавляет: `detected_at`, `statement` (нейтральная формулировка вида
«Эпизод похож на возможное падение»), `image_media_id`, `clip`.

`ClipEvidence`: `status` (`available / preparing / unavailable`),
`duration_seconds` (константа 30), `media_id`, `unavailable_reason`.

### 3.5. Медиа — способ доставки изменился

`GET /latest-image` с двумя JPEG в base64 **исчез**. Вместо него
`GET /api/v1/media/{media_id}` отдаёт двоичный `image/jpeg` или `video/mp4`.

Это снимает главное ограничение, ради которого в
[ADR-0002](adr/0002-kadr-po-zaprosu.md) кадр запрашивался только по кнопке:
медиа больше не едет внутри JSON.

### 3.6. Транспорт

В `servers` добавлен `https://api-demo.example.com` с пометкой про сертификат от
публично доверенного CA. Локальный `http://127.0.0.1:8080` помечен как
«development only, never expose to the Internet». Для эмулятора ТЗ подтверждает
`http://10.0.2.2:8080`.

## 4. Что происходит с текущим кодом

### Выживает без изменений

- Весь каркас: Gradle, version catalog, Hilt, KSP, Navigation, `network_security_config`,
  переходный флаг AGP.
- `core/network/`: `apiCall`, `AuthInterceptor`, `BaseUrlInterceptor`, `ServerUrlHolder`.
- `core/error/`: `AppError`, `ErrorMapper`, `ErrorText` — формат ошибок
  `{code, message}` в контракте не изменился.
- `core/time/TimeFormat`.
- `data/local/`: `KeystoreSecureStorage`, `AppSettings` — потребуется добавить
  хранение второго токена, структура остаётся.
- `ui/common/`, тема, разделение экранов на stateful-обёртку и stateless-содержимое.

### Переписывается

| Что | Почему |
|---|---|
| `data/remote/Dto.kt`, `TerentiyApi.kt`, `Mappers.kt` | другие маршруты, другие схемы |
| `data/repository/AuthRepository.kt` | PIN → логин и пароль, плюс refresh и logout |
| `ui/activation/` | поля: логин, пароль от 12 символов, необязательный e-mail |
| `ui/pin/` → `ui/login/` | экран PIN заменяется экраном входа |
| `ui/home/` | другая модель ответа, добавляется переключатель наблюдения |
| `domain/WatchState.kt` | заменяется состояниями `ObservationStatus` + `camera` |
| `ui/home/ImageSheet.kt` | `latest-image` исчез; кадр приходит из карточки события |
| `HomeViewModel.POLL_INTERVAL_MS` | интервал задаёт сервер через `poll_after_seconds` |

### Добавляется

- `okhttp3.Authenticator` для прозрачного refresh при `401` с учётом ротации:
  параллельные запросы не должны гонять refresh дважды, иначе сработает отзыв
  token family.
- Выход и восстановление пароля.
- Экран истории событий с курсорной пагинацией.
- Карточка события.
- Загрузка медиа по `media_id` с авторизацией.
- Переключатель наблюдения с промежуточными состояниями.

### Отложенные технологии становятся нужны

Room (офлайн-кэш истории), Paging 3 (курсорная пагинация), Coil (кадр по ссылке
с авторизацией), Media3 (30-секундный клип) — всё четыре, ровно как
предполагалось в [`backlog-mobile.md`](backlog-mobile.md) §1.

## 5. Порядок миграции

Предлагаемая последовательность, когда backend будет готов:

| # | Этап | Зависит от backend |
|---|---|---|
| 1 | DTO и `TerentiyApi` по новому контракту, мапперы | нет, можно по контракту |
| 2 | `Session` в защищённом хранилище, `Authenticator` с ротацией | нет |
| 3 | Экраны регистрации и входа | `auth/register`, `auth/login` |
| 4 | Главный экран на `HomeSummary` | `home` |
| 5 | Переключатель наблюдения | `observation` |
| 6 | История событий | `events` |
| 7 | Карточка события и медиа | `events/{id}`, `media/{id}` |
| 8 | Восстановление пароля либо заглушка «Обратитесь к администратору» | `password-reset/*` |

Этапы 1 и 2 не зависят от готовности сервера и могут идти раньше остальных.

## 6. Что нужно от backend

1. **Реализация контракта.** Сейчас ни один из новых маршрутов не существует.
2. **Подключение детекции падения к backend.** Правила из `fall_rules/` работают,
   но результат пишется в отчёт; события до сервера не доходят.
3. **Таблица событий и хранилище медиа.** Схема БД не менялась, `InMemoryImageStore`
   по-прежнему держит одну пару JPEG в оперативной памяти.
4. **Запись 30-секундных клипов** на стороне агента и их передача.
5. **Подтверждение, что `draft` снят** — до этого момента контракт может меняться.

## 8. Состояние на 29 сентября 2026: переход выполнен

Приложение переписано по контракту 1.1.0-draft целиком. Что изменилось
относительно раздела 5 этого документа:

| Этап перехода | Состояние |
|---|---|
| DTO, `TerentiyApi`, мапперы | выполнено, покрыто тестами на MockWebServer |
| `Session` в защищённом хранилище, `TokenAuthenticator` с ротацией | выполнено, см. [ADR-0005](adr/0005-serializatsiya-obnovleniya-sessii.md) |
| Экраны подключения и входа | выполнено, PIN удалён |
| Главный экран на `HomeSummary` | выполнено, интервал опроса берётся с сервера |
| Переключатель наблюдения | выполнено, промежуточные состояния показываются |
| История событий | выполнено, курсорная пагинация |
| Карточка события и медиа | выполнено; кадр показывается, клипа не существует — см. [backlog §14](backlog-mobile.md) |
| Восстановление пароля | заглушка-подсказка, см. [backlog §15](backlog-mobile.md) |

Поскольку backend контракт по-прежнему не реализует, приложение получило второй
источник данных — встроенный демо-сценарий, переключаемый в Профиле
([ADR-0006](adr/0006-dva-istochnika-dannykh.md)). Сетевой путь написан по схеме
и проверяется в день готовности сервера переключением режима, без пересборки.

Заодно закрыта дыра из [backlog §5](backlog-mobile.md): в приложении появился выход
из аккаунта.

Открытым остаётся вопрос из раздела 6: **противоречие между архитектурой А
(изображение не покидает дом) и контрактом, который требует отдавать кадр и клип
через `GET /api/v1/media/{media_id}`.** Приложение исходит из контракта. Если
доказательное медиа останется на edge-узле, удалённый мониторинг работать не будет
— за медиа придётся ходить внутрь домашней сети.
