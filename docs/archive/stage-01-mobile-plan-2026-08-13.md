# План разработки. «Терентий» — Stage 01, мобильное приложение (Android)

**Статус:** утверждён
**Версия:** 1.0
**Дата:** 13 августа 2026 года
**Связанные документы:** `SDD-000_Terentiy.md`, `stage01specification.md`, `stage01mobile.md`
**Контракт:** `contracts/stage01-mobile-api.yaml`

---

## Контекст

Проект «Терентий» (SDD-000) — система поведенческого мониторинга: IP-камера → локальный агент на ноутбуке (декодирование RTSP + ML-детекция) → backend → мобильное приложение. Stage 01 подтверждает работоспособность сквозной архитектуры: локальная детекция человека, событие `person_presence_detected`, доставка события в backend и отображение в приложении.

Мобильное приложение первого этапа — **функциональный прототип**, а не финальный UI. Его задача: показать, что система подключена, видна пользователю и фиксирует присутствие человека.

**Охват этого плана:** Android-приложение детально + контракт `Backend → Mobile` и мок-сервер. Backend, локальный агент и ML описаны только в объёме, необходимом мобильной части. Исполнитель — один разработчик, поэтому план последовательный, с явным критическим путём.

**Ключевое ограничение планирования:** backend Stage 01 разрабатывается параллельно и на старте не готов. Поэтому работа строится **contract-first**: сначала фиксируем OpenAPI-контракт и поднимаем мок, дальше мобильная разработка не блокируется backend'ом ни на один день.

## 1. Технологический стек

### Мобильное приложение

| Область | Выбор | Почему |
|---|---|---|
| Язык | **Kotlin** (не Java) | Корутины/Flow нужны для polling и состояний; вся современная Android-документация и Jetpack — Kotlin-first |
| Минимальный SDK | 26 (Android 8.0), target — актуальный | Покрывает практически весь парк устройств, не тянет legacy-костыли |
| UI | **Jetpack Compose + Material 3** | Экранов мало, состояний много — декларативный UI дешевле для прототипа состояний |
| Архитектура | MVVM + однонаправленный поток (UiState → ViewModel → Repository) | Стандарт, легко тестировать, легко расширять на Stage 02 |
| Модульность | Один модуль `:app` с package-by-feature | Для одного разработчика мультимодульность — преждевременная стоимость; разделение по пакетам оставляет путь к модулям |
| DI | **Hilt** | Минимум boilerplate, нужен для подмены источников данных в тестах |
| Сеть | **Retrofit + OkHttp + kotlinx.serialization** | Стандарт, есть интерцепторы для токенов и логирования |
| Асинхронность | Coroutines + Flow | Polling, lifecycle-aware подписки |
| Локальное хранение | **Room** (кэш событий и статуса), **DataStore** (настройки) | Журнал должен открываться офлайн с пометкой «данные устарели» |
| Токены | **EncryptedSharedPreferences** (Jetpack Security) | Access/refresh токены не должны лежать в открытом виде |
| Изображения | **Coil** (через общий OkHttp с авторизацией) | Контрольное изображение отдаётся по защищённой ссылке |
| Видео | **Media3 / ExoPlayer** | Короткий тестовый фрагмент (mp4/HLS) |
| Навигация | Navigation Compose (type-safe routes) | 4 экрана, нужен только backstack и deep-link на карточку события |
| Сборка | Gradle KTS + version catalog (`libs.versions.toml`) | Один источник версий |
| Тесты | JUnit + **MockWebServer** + Turbine + Compose UI Test | Контрактные и state-тесты дают основную ценность на прототипе |
| Диагностика | Timber + опционально Crashlytics/Sentry | Внутренние логи; пользователю технические коды не показываются |

### Смежные компоненты (ориентир, детали вне этого плана)

- **Локальный агент:** Python (OpenCV/FFmpeg для RTSP, ONNX Runtime или Ultralytics YOLO для детекции `person`), локальная очередь на SQLite.
- **Backend:** Python FastAPI (или Kotlin/Ktor, если хочется один язык с мобильным) + PostgreSQL для метаданных + S3-совместимое хранилище (MinIO локально) для медиа.
- **Транспорт:** HTTPS, JSON, аутентификация Bearer-токеном; медиа — по короткоживущим подписанным ссылкам.

Эти решения стоит зафиксировать отдельными ADR — SDD-000 §12 явно оставляет их за рамками.

## 2. Контракт `Backend → Mobile`

Полный контракт: **`contracts/stage01-mobile-api.yaml`** (OpenAPI 3.1). Он — источник истины для обеих сторон; этот раздел лишь резюмирует его.

Эндпоинты (префикс `/api/v1`):

```
POST /auth/login          → пара токенов
POST /auth/refresh        → новая пара токенов
GET  /system/status       → состояние камеры, агента, присутствия + server_time
GET  /events?limit&cursor → страница журнала (курсорная пагинация)
GET  /events/{eventId}    → карточка события со ссылкой на медиа
```

### Решения, требующие явного подтверждения у автора SDD

1. **`UNKNOWN` ≠ «человека нет».** SDD-000 §6 и §11 требуют не смешивать эти состояния. Даже на Stage 01 API возвращает `UNKNOWN` отдельным значением — иначе на Stage 02 придётся ломать контракт.
2. **Медиа отделено от метаданных.** SDD-000 §6: событие сохраняется и отображается, даже если изображение ещё грузится или недоступно. Поэтому `media.state` — обязательное поле, а не отсутствие блока.
3. **Идемпотентность (FR-09)** — ответственность связки agent→backend; мобильному клиенту важно лишь, что `event_id` стабилен и годится как ключ кэша.
4. **Курсорная пагинация, не offset** — журнал растёт с головы, offset даёт дубли и пропуски.
5. **`server_time` обязателен** — свежесть считается относительно сервера, а не часов телефона.
6. **Push не входит в Stage 01** (spec §5) — обновление polling'ом и pull-to-refresh.

### Мок-сервер

```bash
npm install -g @stoplight/prism-cli
prism mock contracts/stage01-mobile-api.yaml --port 4010
```

Сценарии выбираются заголовком `Prefer: example=<имя>`. Доступны: `all_ok`, `person_not_present`, `camera_unavailable`, `agent_unavailable`, `reconnecting`, `stale` для `/system/status`; `page`, `empty`, `last_page` для `/events`; `media_available`, `media_uploading`, `media_unavailable` для карточки события.

## 3. Модель состояний в приложении

Самая содержательная часть прототипа: спецификация мобильного приложения на 70% состоит из состояний, а не из экранов.

**Состояние устройства** (`camera` / `agent`) в пользовательских формулировках:

| Домен | Что видит пользователь |
|---|---|
| `ONLINE` и данные свежие | «Система работает» |
| `RECONNECTING` | «Соединение восстанавливается» |
| `UNAVAILABLE` (camera) | «Камера недоступна» |
| `UNAVAILABLE` (agent) | «Локальный агент недоступен» |
| `UNKNOWN` / данные устарели / нет сети у телефона | «Данные временно не обновляются» |

**Свежесть** вычисляется на клиенте: `server_time − last_seen_at > STALE_THRESHOLD` (стартовое значение 90 c, вынести в конфиг) ⇒ независимо от `state` показываем «данные временно не обновляются». Отдельно учитывается возраст последнего *успешного* ответа самого приложения.

**Состояние медиа события:** `AVAILABLE` → показать; `UPLOADING` → «медиаматериал загружается» + возможность повторить; `UNAVAILABLE` → «медиаматериал недоступен»; ошибка сети при открытии → «не удалось загрузить, проверьте соединение» + retry.

**Что приложение не показывает никогда** (stage01mobile.md §6): bounding boxes, confidence, параметры RTSP, внутренние ID, системные журналы, ML-пороги. Этих полей нет в контракте намеренно — проще не получать, чем не показывать.

## 4. Экраны

1. **Вход** — email/пароль, инлайн-ошибка, состояние загрузки, автологин при валидном refresh-токене.
2. **Главный** — крупный статус присутствия, карточки «Камера» и «Локальный агент», «Последняя связь: N минут назад», переход в журнал, pull-to-refresh, баннер устаревания данных.
3. **Журнал событий** — список с курсорной пагинацией, группировка по дням, в строке: время, «Обнаружен человек», камера/помещение, иконка наличия медиа и его статуса; pull-to-refresh; пустое состояние; офлайн-состояние поверх кэша.
4. **Карточка события** — дата/время, источник, контрольное изображение (zoom) или плеер фрагмента, состояние медиаматериала, retry.

**Обновление данных:** lifecycle-aware polling (`repeatOnLifecycle(STARTED)`) — 20 с на главном экране, 60 с в журнале, + обновление при возврате на экран, + ручной pull-to-refresh. Никаких фоновых сервисов на Stage 01.

## 7. Проверка результата

**Автоматически:**

- `./gradlew test` — маппинг DTO→domain, вычисление свежести/устаревания, логика retry и refresh токена.
- MockWebServer-тесты репозиториев: 200, 401 + успешный refresh, 401 + неуспешный refresh (логаут), 404, 500, таймаут, невалидный JSON.
- Compose UI-тесты: вход (ошибка), главный (5 состояний из §3), журнал (пусто / список / офлайн), карточка (медиа доступно / грузится / недоступно).
- CI прогоняет тесты и lint на каждый push.

**Вручную — по критериям приёмки stage01mobile.md §7:**

1. вход в приложение; 2. виден статус камеры и агента; 3. виден список событий; 4. открывается карточка; 5. просматривается изображение/видео; 6. понятное состояние при отсутствии медиа; 7. корректное состояние при недоступности камеры или агента.

**Сквозной прогон Stage 01** (мобильная часть): человек входит в кадр → событие появляется в приложении в течение одного цикла polling; выключить камеру → «Камера недоступна» и присутствие `UNKNOWN`; остановить агента → «Локальный агент недоступен»; отключить backend и вернуть → события из локальной очереди агента появляются без дублей; выключить сеть на телефоне → журнал открывается из кэша с пометкой об устаревании.

## 8. Риски мобильного трека

| Риск | Смягчение |
|---|---|
| Контракт меняется после начала разработки | Contract-first, OpenAPI под ревью автора SDD до P1; изоляция DTO от доменных моделей — правки локализуются в мапперах |
| Backend не готов к P8 | Мок покрывает все сценарии; P0–P7 полностью независимы |
| Подписанные ссылки на медиа истекают, пока пользователь смотрит карточку | Обработка 403/410 → тихий перезапрос карточки события, а не ошибка пользователю |
| Polling сажает батарею | Только при видимом экране, никаких фоновых сервисов на Stage 01; интервалы в конфиге |
| Соблазн показать ML-детали «для отладки» | Технические поля не включены в контракт вообще (§3) |
| «Данные не обновляются» путается с «человека нет» | Отдельная доменная модель состояний, unit-тесты на матрицу — прямое требование SDD-000 §6 |

## 10. Принятые решения

Зафиксировано 13 августа 2026 года.

| Вопрос | Решение |
|---|---|
| Контракт `Backend → Mobile` | **Согласован.** `contracts/stage01-mobile-api.yaml` — источник истины, включая три состояния присутствия и отделение медиа от метаданных |
| Аутентификация | **Свой email/пароль + JWT.** Внешний провайдер не используется. Контракт уже описывает `/auth/login` и `/auth/refresh` |
| Формат видеофрагмента | **mp4 целиком** (`content_type: video/mp4`). Проще для Media3 и достаточно для короткого контрольного фрагмента. HLS при необходимости добавляется позже новым значением, без слома контракта |
| Целевые устройства | Конкретного списка нет. Рабочее допущение: телефоны с **Android 12–16**, разрешения 1080×2400 и 1440×3120, основной эмулятор для разработки — **Pixel 7, API 35** |
| Состояния от backend на старте | Backend реализует только `all_ok` и `camera_unavailable`. Остальные значения enum зарезервированы; клиент обязан обрабатывать их с первого дня и не падать на неизвестном значении |

### Следствия для реализации

- **Enum'ы в DTO — с fallback.** kotlinx.serialization по умолчанию бросает исключение на неизвестном значении enum. Все перечисления из контракта маппятся через кастомный сериализатор: неизвестное значение → `UNKNOWN`, а не крэш. Это единственный способ не сломать приложение в момент, когда backend начнёт отдавать `RECONNECTING`.
- **Экраны под все состояния строятся сразу.** Сценарий `camera_unavailable`, который backend отдаёт уже сейчас, приводит присутствие в `UNKNOWN` — то есть «наблюдение недостоверно» это сегодняшний экран, а не будущий.
- **Медиа в моке.** Prism отдаёт ссылку на несуществующий домен, поэтому для проверки карточки события нужен локальный статический сервер (`npx serve mock/media`) и два тестовых файла: кадр с человеком и короткий mp4.

### Остаётся открытым

1. Кто владеет оригиналом OpenAPI-файла, если появится второй репозиторий (backend). Сейчас оригинал — здесь.
2. Срок жизни подписанных ссылок на медиа — влияет на логику перезапроса карточки.
